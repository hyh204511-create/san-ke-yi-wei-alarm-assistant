# 三客一危值班助手：数据展示、日报月报与导出规划

版本：`2.1`
形成日期：`2026-07-22`
状态：实现计划基线；实际能力以代码、测试和真实授权联调证据为准。

## 1. 产品边界

数据展示与导出建设为独立“数据与报表中心”，与浏览器插件的实时报警操作分开。插件只展示当前工作所需状态和待办；正式日报、周报、月报、车辆监控日报、企业对比和历史导出在报表中心完成。

本计划覆盖两类报表和受控处置编排：第一类是按企业拆分的报警日报、周报、月报；第二类是车辆监控日报；处置编排支持在授权规则下顺序执行语音对讲和文本/TTS。未完成客户授权、指定实车范围、人工值守安排和平台回执核验前，真实文本下发和语音对讲适配器必须阻断，仅允许演练或沙箱运行。

## 2. 数据主题

| 主题 | 主要数据 |
| --- | --- |
| 报警事实 | 报警 ID、类型、时间、车辆、企业、位置、速度、平台状态 |
| 处置过程 | 规则、处理策略、文本/语音尝试、人工任务、开始结束时间 |
| 处置结果 | 成功、失败、未知、转人工、完成、复核 |
| 组织企业 | 集团、分公司、企业、车辆归属和历史归属快照 |
| 数据质量 | 缺字段、冲突、接口错误、页面变化、同步延迟 |
| 审计 | 规则、处置、导出和敏感访问 |
| 报表来源批次 | 报表查询、车辆基础信息、轨迹明细的请求批次和数据截止时间 |
| 车辆监控日报事实 | 末次定位日期、上线状态、里程状态、过滤原因和关联异常 |

## 3. 页面结构

1. 运行概览：当前报警、待人工、超时、文本/语音通道状态。
2. 企业驾驶舱：授权企业的报警、处置和趋势。
3. 处置台账：可查询的事件、动作、人工任务和最终结果。
4. 日报中心：按日期和企业生成、查看和下载。
5. 周报中心：按周和企业生成、查看和下载。
6. 月报中心：按月份、集团/分公司/企业生成和归档。
7. 车辆监控日报：按目标日查看正式数据、过滤清单和异常清单。
8. 导出任务：查看生成进度、失败原因、审核状态、下载记录和过期时间。
9. 数据质量：缺字段、冲突、接口变化、关联异常和异常来源。

## 4. 报警报表口径建议

第一类报表统一使用省平台“报表查询”作为正式取数入口，不以实时报警页面或单一报警查询接口替代正式报表底表。查询维度选择“车辆”，车辆、企业和报警相关范围必须完整勾选，整体取数后再按企业拆分。

- 报警日报、周报、月报使用服务器接收时间归属统计周期，并保存北京时间、查询参数和数据截止时间。
- `REALTIME` 与 `PENDING` 在报表和插件用户界面归为同一类“正式报警”，内部继续保存 `sourceKind`、来源接口和来源顺序。
- `TECHNICAL` 保留为正式技术检测事件；`PREWARNING` 只作为预警事实，不计入正式正报；`HISTORY` 只用于历史补采、复盘和核对。
- 月报中的“正报”按已去重的 `REALTIME` 事实统计；不能用 `PREWARNING` 或 `positiveReportingFlag` 替代。
- 报表必须保留来源批次、字段完整性、重复数据、字段冲突和接口异常结果。

报表类型固定为：

```text
ALARM_DAILY
ALARM_WEEKLY
ALARM_MONTHLY
```

周起止规则、日报生成时间、月报截止时间和迟到数据补数规则必须配置化；正式模板确认前不得由实现人员自行改变统计口径。

### 4.1 常规报表固定提取步骤

日报、周报、月报共用同一套提取流程，仅时间范围不同：

1. 登录平台，进入“报表查询”，不得使用“报警查询”代替。
2. 维度必须选择“车辆”，不选择“机构”；企业信息通过车辆所属关系带出。
3. 车辆状态同时勾选“营运”和“营运不考核”。
4. 机构（企业）不单独选择，查询一次性覆盖所有企业车辆。
5. 报警类型点击“全选”，避免默认考核项过滤造成漏数。
6. 时间范围按周期设置：日报取前一天，周报取周一至周日，月报取完整自然月；时间字段必须选择“服务器接收时间”。
7. 查询后导出一个包含全部企业车辆的原始 Excel；当前业务流程由人工按“所属机构”字段拆分，为每个企业生成独立工作簿，后续自动化必须复现同一拆分口径。
8. 每个企业工作簿固定包含三个子表，顺序为“处置率”“处理率”“报警中心数据”，字段和样式按运营团队模板整理。

常规报表建议在凌晨 00:00 后提取前一日数据，等待平台数据稳定；具体调度时间和补数规则仍记录在报表快照中。

- 统计日期和数据截止时间。
- 组织、企业和车辆数量。
- 报警总量及类型分布。
- 自动文本计划数、成功数、失败数和成功率。
- 自动语音计划数、成功数、失败数和成功率。
- 文本升级语音次数。
- 自动转人工数量、人工完成量和未完成量。
- 平均首次响应时间、平均处置时长和超时量。
- 高频报警车辆和主要失败原因。
- 缺字段、冲突和接口异常数量。

## 5. 周报与月报口径建议

周报在日报指标基础上增加周内趋势、企业对比和重复报警车辆；周起止日以业务确认的周历为准，并记录在快照中。

- 月份、统计范围、数据截止时间和报表模板版本。
- 集团、分公司、企业和车辆规模。
- 报警总量、类型分布、日趋势和环比。
- 处置完成率、自动响应率、人工接管率和超时率。
- 文本、语音和组合策略的成功率。
- 重复报警车辆、高风险事件和未闭环事件。
- 企业间对比和排名；是否开放由权限决定。
- 数据完整率、冲突率和接口异常。
- 规则版本变更对统计口径的影响说明。

## 6. 报表生成流程

```mermaid
flowchart LR
    A["报表员选择企业、周期和模板"] --> B["权限与企业范围校验"]
    B --> C["冻结查询参数和数据截止时间"]
    C --> D["调用报表中心并记录来源批次"]
    D --> E["标准化、去重和完整性校验"]
    E --> F["按企业生成 ReportSnapshot"]
    F --> G["生成三子表 XLSX"]
    G --> H["人工审核、记录哈希和下载审计"]
    H --> I["授权下载与归档"]
```

报表必须可复现：相同快照、相同模板版本应得到相同结果；后续数据变化不能修改已经归档的报表。

报警日报、周报、月报使用服务器接收时间归属统计周期；车辆监控日报使用目标日 D 的末次定位日期判定上线状态。迟到数据、平台补数或口径修正不能覆盖已发布快照，必须生成带更正原因和差异说明的新版本；车辆和企业维度使用事件发生时的归属快照。

## 7. 导出类型

| 类型 | 典型格式 | 数据范围 | 权限 |
| --- | --- | --- | --- |
| 报警日报/周报/月报 | XLSX | 按企业拆分的报警、处置和质量指标；每个工作簿包含三个固定子表 | 报表员及授权管理人员 |
| 车辆监控日报 | XLSX | 正式车辆状态、过滤清单和关联异常 | 具有相应车辆范围权限的报表员 |
| 脱敏明细 | XLSX/CSV | 经授权的业务明细和掩码字段 | 具有明细权限的报表员 |
| 内部处置台账 | XLSX | 授权企业业务明细 | 处置复核员/报表员 |
| 敏感证据包 | 加密 JSON/受控压缩包 | 完整明细和证据引用 | 专门权限或审批 |

## 8. 查询与导出接口对象

常规报警报表的查询参数必须显式记录，避免实现人员遗漏平台筛选条件：

```text
ReportQuery
reportType = ALARM_DAILY | ALARM_WEEKLY | ALARM_MONTHLY
dimension = VEHICLE
vehicleStatus = [OPERATING, OPERATING_NOT_ASSESSED]
enterpriseSelection = ALL_BY_VEHICLE_AFFILIATION
alarmTypeSelection = ALL
timeBasis = SERVER_RECEIVED_AT
period / dataCutoffAt / templateVersion
```

原始查询结果先保存为一个全量来源批次，再按 `所属机构` 拆分为企业工作簿；企业拆分不是平台查询条件，不能为了省事改成逐企业查询并据此宣称已覆盖全部车辆。

车辆监控日报和轨迹完整率使用独立的来源查询对象，分别记录机构全选、车辆状态、目标日和联网联控权限结果。

## 9. ExportJob

每次导出记录：

```text
exportJobId
requestedBy / requestedRole
organizationScope / enterpriseScope
reportType / templateVersion
filters / period / timeBasis / dataCutoffAt
sourceBatchId / validationStatus / reviewStatus
sensitivityLevel / maskingPolicy
purpose / approvalId
status / failureReason
fileName / fileHash / expiresAt
createdAt / completedAt / downloadedAt
```

报表类型：

```text
ALARM_DAILY | ALARM_WEEKLY | ALARM_MONTHLY | VEHICLE_MONITOR_DAILY
```

状态：

```text
CREATED → AUTHORIZING → GENERATING → VALIDATING → REVIEW_REQUIRED → READY
                                                        ↘ FAILED
READY → DOWNLOADED / EXPIRED
```

## 10. 完整 JSON 管控

完整 JSON 不在普通报表页面直接提供。确需技术排障、审计或证据核查时，使用“敏感证据包”流程：

1. 选择明确事件和最小时间范围。
2. 展示将包含的敏感字段。
3. 填写用途和接收范围。
4. 校验专门权限或审批。
5. 再次执行凭证脱敏，禁止包含 Cookie、Token 和密码。
6. 生成文件哈希、过期时间和下载审计。
7. 文件进入受控目录或加密存储。

## 12. 报警日报、周报、月报实现计划

### 12.1 取数与标准化

1. 从已授权的省平台报表中心获取数据，使用车辆维度和服务器接收时间。
2. 冻结查询周期、企业范围、车辆范围、报警范围、模板版本和数据截止时间。
3. 记录每次请求的 `sourceBatchId`、接口、响应状态、字段版本、页码和采集时间；不保存认证凭证。
4. 将平台结果标准化为报警事实、处置事实和数据质量事实，优先按平台报警 ID 去重；缺少稳定 ID 时标记为待核对，不静默合并。
5. 完整性校验失败、字段冲突、接口失败和分页不完整必须使任务进入 `FAILED` 或 `REVIEW_REQUIRED`，不得生成看似完整的正式报表。

### 12.2 企业拆分与导出

- 整体取数和校验完成后，按企业归属快照拆分；每家企业生成一个 XLSX 工作簿。
- 每个工作簿按固定顺序包含三个子表：“处置率”“处理率”“报警中心数据”。字段顺序、汇总行、表头样式和格式以运营团队模板为准；模板细节确认前只生成内部验证文件，不称为正式报表。
- 日报先实现，周报和月报复用同一套取数、归并、校验、快照和导出逻辑，仅替换周期聚合器和模板。
- 已发布快照不可覆盖；迟到数据、平台补数或口径修正必须生成更正版，并保存差异原因、原版本和新版本关系。
- 支持人工审核、单个下载和批量下载；每次生成、审核、下载、过期和删除均写入审计。

## 13. 车辆监控日报实现计划

车辆监控日报类型固定为 `VEHICLE_MONITOR_DAILY`，目标日记为 D，默认在 D+1 生成。

### 13.1 两个来源

| 来源 | 用途 | 必须保留 |
| --- | --- | --- |
| 报表中心 → 车辆基础信息 | 车辆、企业和基础属性底表；机构全选、车辆状态选“营运”和“营运不考核”；不设置时间范围 | 来源批次、查询参数、字段版本 |
| 系统设置 → 联网联控 → 考核明细 → 轨迹完整率明细 | 目标日前一天的轨迹完整率、总里程和在线轨迹判断；需要专用账号权限 | 来源批次、目标日期、响应状态、权限结果 |

车辆基础信息一次性导出全部车辆，按 `末次定位时间` 的日期与目标日 D 比较；轨迹完整率只处理该报表有数据的车辆，未上线车辆无轨迹数据时不强行补行。两个来源必须先分别校验，再按稳定车辆标识关联；不能唯一关联时进入异常清单，禁止使用不确定的模糊匹配直接进入正式日报。

### 13.2 结果分类

- `末次定位时间` 的日历日期等于 D：标记为“上线”。
- `末次定位时间` 的日期早于 D：标记为“未上线”。
- `末次定位时间` 为空：标记为无末次定位并进入过滤清单，不计入正式“未上线”统计。
- 未上线车辆在轨迹完整率明细中无数据时，不补造轨迹记录，只保留车辆日报的状态。
- 轨迹完整率为 100%：标记为“正常”。
- 轨迹完整率小于 100%：标记为“轨迹不完整”。
- 车辆已上线、轨迹完整率为 0% 且总里程为 0：优先标记为“有在线无轨迹”；该状态不能被普通的完整率分类覆盖。
- 两个来源无法唯一关联、关键字段冲突或来源批次不完整：进入异常清单。

正式日报、过滤清单和异常清单都必须保留 `sourceBatchId`；过滤和异常记录必须分别写入 `filterReason`、`anomalyReason`，便于复核和重新生成。

## 14. 文本下发与语音对讲实现计划

### 14.1 动作前置闸门

只有以下条件全部满足，才允许进入真实适配器；否则写入 `BLOCKED` 或 `MANUAL_REQUIRED`：

- 使用已审核并已发布的规则、文本模板和语音资产。
- 当前账号、企业范围、值班班次、平台会话、车辆范围和设备动作租约有效。
- 车辆属于明确授权的测试车辆或已完成生产授权的车辆。
- 平台接口契约、回执字段和失败码已经过授权联调。

未满足条件时只能运行演练或沙箱，不触发省平台业务动作。

超时/超速车辆的实车验证可以作为正式联调场景：当没有独立测试车辆时，只能在项目负责人和客户明确授权的车辆范围内进行，并且必须有人工值守、固定审核话术、可回退的人工处理和完整审计；不能因为缺少测试车辆就自动放开全部生产车辆。

### 14.2 顺序编排与结果

支持经规则明确声明的 `VOICE_THEN_TEXT` 策略：

```text
语音对讲开始
→ 语音通道结束并取得可验证终态
→ 顺序发送文本/TTS
→ 分别记录回执和最终处置状态
```

在已授权的超时/超速实车场景中，系统按规则自动执行“语音对讲 + 文本/TTS”，但两者必须顺序执行：语音取得可验证结束结果后才发送文本。文本或语音失败、超时、未知、阻断时立即转人工兜底，不伪造成功。动作状态统一使用：

```text
PLANNED → EXECUTING → SUCCEEDED / FAILED / UNKNOWN / BLOCKED / MANUAL_REQUIRED
```

失败可按已发布规则重试；超过规则时限仍无明确成功必须通知人工。系统只记录动作回执和证据，不自动判断司机是否纠正、不自动确认查岗、不自动判定正报或处罚责任。

## 15. 分阶段实施与版本交付

1. **需求冻结**：确认三个报警子表的字段和格式模板、周起止规则、报表截止时间、企业关系、账号权限、车辆范围、实车测试范围和真实动作授权。
2. **接口契约**：核验报表中心、车辆基础信息、轨迹完整率、文本/TTS和语音对讲接口；只从用户已打开且已登录的浏览器会话取真实证据，助手不新开浏览器、不点击平台业务按钮。
3. **报警日报**：完成报表查询、标准化、去重、完整性校验、全量原始 Excel、按“所属机构”人工/系统拆分和三子表 XLSX。
4. **报警周报/月报**：复用日报底座，增加周期聚合、趋势、企业对比和更正版快照。
5. **车辆监控日报**：完成双来源批次、关联、正式数据、过滤清单和异常清单。
6. **任务与审计**：接入任务调度、审核、单个/批量下载、文件哈希、过期和删除审计。
7. **受控处置**：先完成演练/沙箱状态机，再在明确授权的超时/超速实车范围内验证语音结束后文本/TTS顺序、回执和人工接管；没有独立测试车辆时不得省略授权和人工值守。
8. **交付同步**：每次功能、采集规则或安全规则变更分别测试、检查、提交独立 Git commit 并推送到已确认远程分支；部署时只部署已推送且确认的 `server/` commit。

## 16. 验收与未决边界

验收必须覆盖：

- 日报、周报、月报的周期边界、企业拆分、三子表结构、字段完整性、重复数据和迟到数据更正。
- 常规报表筛选条件：车辆维度、营运/营运不考核、机构不单选、报警类型全选、服务器接收时间，以及全量导出后按“所属机构”拆分。
- `REALTIME`、`PENDING`、`TECHNICAL`、`PREWARNING`、`HISTORY` 的来源分类和统计边界。
- 车辆日报的 D/D+1 生成、车辆状态筛选、等于 D、早于 D、空日期过滤、唯一关联失败和来源批次追溯。
- 轨迹完整率的 100% 正常、小于 100% 不完整、总里程为 0 的在线无轨迹和未上线无数据边界。
- 语音后文本顺序、禁止并发、失败/超时/未知转人工、未授权阻断和动作审计。
- 真实平台验证只能使用用户已打开的已登录浏览器连接；当前文档更新不代表真实报表接口或真实动作已经验收。

以下事项在业务确认前不得由实现人员自行写死：三个子表的字段和样式细节、周历定义、报表生成时间、数据截止和补数规则、企业权威关系、联网联控账号权限、实车测试授权、语音回执成功标准、动作重置与重试参数。
