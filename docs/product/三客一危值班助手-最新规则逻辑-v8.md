# 三客一危值班助手：最新规则逻辑 V8

版本：`8.0`  
日期：`2026-07-21`  
对应代码：扩展 `0.5.4`、Linux + 云 PostgreSQL 部署准备  
状态：当前需求基线；正式真实动作仍需测试车辆验收。

## 1. 报警来源和处理范围

| 来源 | 含义 | 行为 |
| --- | --- | --- |
| `REALTIME` | 平台已判定成立的正式实时报警 | 进入优先队列，按规则动作 |
| `TECHNICAL` | 技术检测正式事件 | 进入优先队列，按规则动作或转人工 |
| `PENDING` | 报警预处理页正式待处理报警 | 进入优先队列，按规则动作 |
| `PREWARNING` | 实时监控页预警列表，平台尚未升级的预报警 | 实时监听、展示、入库，不自动动作 |
| `HISTORY` | 历史查询或补采数据 | 只用于复盘、核对和报表 |

优先队列固定为：

```text
REALTIME + TECHNICAL + PENDING
```

报警升级、解除、超速持续时间和平台状态变化由省平台判定，插件只负责读取、规则匹配、动作执行/记录和报表数据保存。

## 2. 实时采集

- 优先监听省平台实际 `fetch/XMLHttpRequest` 数据，不主动制造页面点击。
- 实时监控页无新数据时不重复写入；数据发生变化立即标准化和同步服务器。
- 如平台接口不主动推送而必须轮询，使用受控白名单接口，默认间隔3秒，不允许任意接口轮询。
- 轮询请求不能重叠；401/403、验证码、人机挑战或连续失败时停止并通知人工。
- 后台中心保存 `AlarmFact`，每个浏览器和省平台账号保存独立 `CaptureSource`。
- 同一报警的重复处理状态只保留一条主事实；同类型报警多次触发时，报表按确认的时间窗口保留最后一条。

## 3. 规则模型

规则由后台配置、审核、发布，插件只加载已发布版本。司机提醒和完成判定的首版矩阵、语音必做/语音优先、内部确认和无法判断转人工口径见[司机提醒与纠正检测规则 V1](司机提醒与纠正检测规则-v1.md)。

每个自动规则默认只有一个主动作渠道；只有在 `reminderPolicy.secondaryChannelMode` 明确为 `ON_PRIMARY_FAILURE` 或 `AFTER_PRIMARY_SUCCESS` 时，才允许配置第二个文本/TTS渠道。

### 3.1 文本终端 TTS

```json
{
  "handlingMode": "AUTO",
  "channels": [{
    "type": "TEXT",
    "terminalTts": true,
    "templateId": "text-fatigue-v1",
    "recipientType": "DRIVER_TERMINAL"
  }],
  "channelStrategy": "SINGLE"
}
```

### 3.2 自动语音对讲

```json
{
  "handlingMode": "AUTO",
  "channels": [{
    "type": "VOICE",
    "assetId": "voice-fatigue-v1",
    "spokenTemplate": "驾驶员，平台已报警，请立即安全停车休息。",
    "recipientType": "DRIVER_TERMINAL"
  }],
  "channelStrategy": "SINGLE",
  "allowRealIntercom": true
}
```

`VOICE` 在本产品中表示 AI 按固定语音资产自动发起平台语音通道并播放语音，不表示人工实时通话。当前没有测试车辆，真实 `VOICE_INTERCOM` 适配器仍然阻断；沙箱可以验证规则、状态和模拟回执。

## 4. 动作结果和重试

统一状态：

```text
PLANNED → EXECUTING → SUCCEEDED
                    ↘ FAILED
                    ↘ UNKNOWN
                    ↘ BLOCKED
                    ↘ MANUAL_REQUIRED
```

规则：

- 明确 `SUCCEEDED`：记录平台回执，流程结束。
- 明确 `FAILED`：允许短间隔重试，默认5秒和10秒各一次。
- 30秒内仍没有明确成功：必须转当前值班人员处理。
- `UNKNOWN`、超时、接口没有可验证回执：不自动重试，直接通知值班人员。
- `BLOCKED`：记录阻断原因，不伪造成功。
- 失败、超时和未知都要进入台账、工单和审计。
- `VOICE_INTERCOM` 明确成功后仍生成 `VOICE_REVIEW_REQUIRED` 未读通知，提醒当前值班人员审核动作回执和可用语音证据；这不等同于司机已经回复。
- 不默认在 `TEXT_TTS` 与 `VOICE_INTERCOM` 之间切换；只有规则明确声明 `ON_PRIMARY_FAILURE` 或 `AFTER_PRIMARY_SUCCESS`，且通过渠道顺序和回执安全闸门时，才允许执行第二个文本/TTS渠道。结果未知、超时或阻断时禁止自动切换。

## 5. 自动语音对讲技术边界

已确认的启动链路：


```text
规则命中
→ 检查助手权限、企业范围、班次、平台会话、车辆白名单和设备租约
→ 调用省平台实时音频启动信令
→ 获取 httpUrl/fileName
→ 建立平台音频通道并播放固定语音
→ 记录启动、发送、回执、保活和关闭结果
```

当前缺少测试车辆，因此以下内容尚未完成真实验收：WebSocket鉴权、音频帧格式、服务端回传、保活周期、关闭码、设备离线和通道占用错误。没有测试车辆前不得把沙箱成功说成真实成功。

## 6. 人工通知

失败、超时、未知、账号挑战和登录退出时通知当前登录的值班人员；`VOICE_INTERCOM` 成功后也产生审核提醒。服务器现在提供中央未读通知、通知确认和动作结果审计接口；网络电话、短信或移动端通知仍另行调研，不写死在报警动作中。司机回传录音/转写策略默认关闭，只有管理员启用并取得可审计同意后才允许登记。

## 7. 会话保活和无人值守

- 所有独立省平台账号适用30分钟保活策略。
- 保活仅在平台授权的报警预处理页执行唯一“查询”按钮。
- 实时监控页不执行保活按钮点击；页面不在目标路由时返回 `ROUTE_NOT_APPROVED`。
- 登录页、挑战页和验证码只识别并通知人工，不自动绕过。
- 浏览器可以短时无人值守；设备心跳、采集、服务器去重和后台存储继续工作。
- 同一省平台账号禁止同时由多个设备使用，服务器拒绝第二台设备注册。

## 8. 服务器和报表数据

- 生产系统使用 Linux + Django/Gunicorn + 云 PostgreSQL。
- 报警事实、处置工单、审计和原始加密抓取目标保留1年。
- 报表按报警发生时间、北京时间统计。
- 支持企业、集团、分公司分别生成报表。
- 当前只导出 Excel（XLSX），不提供 PDF。
- 车牌、司机和位置暂按客户确认的不脱敏要求处理，但访问仍受助手账号、企业范围和审计控制。

## 8.1 月报“正报”统计口径（客户已确认）

月报中的“正报”直接取省平台来源为 `REALTIME` 的正式实时报警，不再把 `PREWARNING` 预警或 `positiveReportingFlag` 当作正报总数。

```text
positiveReportTotal = count(server-deduplicated AlarmFact where source_kind = REALTIME)
positiveReportTypeCounts = group the same facts by alarm_name
```

因此，抽烟报警、生理疲劳报警、超速报警、接打手持电话报警、摄像头偏离驾驶位报警等正报类型，均从 `REALTIME` 事实按报警名称统计。申诉、核验、文本/TTS、语音动作回执只记录为正报后的处置结果，不改变正报事实归属。
