# 三客一危省平台 AI 报警处置助手项目建设方案

文档版本：V1.1（客户沟通版）

文档用途：项目沟通、需求确认、建设范围确认、实施与验收依据

## 第1章 需求梳理

### 1.1 项目背景

湖南省交通运输车辆动态监管场景中，三客一危车辆监管平台已经具备报警生成、报警详情查看、视频查看、文本下发、语音对讲、报警查询、证据导出和申诉处理等基础能力。客户当前面临的主要问题，不是缺少一个新的监管平台，也不是缺少报警识别能力，而是报警产生后的第一处置链路仍然高度依赖人工值守。

在实际值守过程中，监控人员需要持续盯屏、快速打开报警、判断报警类型、查看视频、选择提醒方式、对司机进行文字或语音干预，并在司机未纠正、风险持续或无法判断时及时通知值班业务人员和企业负责人。该过程高频、重复、责任压力大，且处置记录如果不能完整留痕，后续复盘、检查和责任说明都会变得困难。

本项目拟建设一套 **三客一危省平台 AI 报警处置助手**。系统以浏览器插件方式运行在现有省平台页面之上，通过 DOM 读取、页面自动化、规则引擎、VLM 视频帧辅助判断、LLM 话术与摘要生成、本地语音模型播放、短信通知和 AI 处理记录台账，帮助客户把报警后的第一处置动作转化为标准化、可追踪、可复核的工作闭环。

### 1.2 建设目标

首版建设目标如下：

1. 建立省平台报警弹窗、报警列表和报警详情的稳定监听与字段读取能力。
2. 建立官方报警规则与客户处置 SOP 的结构化匹配能力。
3. 建立按报警类型选择文本下发、语音对讲、内部确认或暂不处理的处置规则。
4. 建立基于固定审核话术的司机提醒机制，避免 AI 自由发挥造成责任边界不清。
5. 建立提醒后的纠正检测机制，对已纠正、未纠正、无法判断和高风险报警进行分类。
6. 建立值班业务人员短信通知和事件详情页，确保异常报警及时被人工接收。
7. 建立企业负责人沟通话术生成、一键复制和人工拨打电话入口。
8. 建立 AI 处理记录台账，完整记录识别、提醒、检测、短信、查看、复制、拨打和人工确认过程。

### 1.3 关键规则速查

| 事项 | 建议规则 |
| --- | --- |
| 项目边界 | 不重建省平台，不替代省平台，不重新实现报警识别，不替代人工承担最终处置责任。 |
| 技术形态 | 首版采用浏览器插件方式，基于省平台页面 DOM、弹窗、按钮和视频区域进行辅助自动化。 |
| 报警读取 | 优先监听报警弹窗；弹窗不可用时从报警列表兜底；读取失败必须提示人工接管。 |
| 司机提醒 | 不默认文本和语音都做；按官方规则和客户 SOP 选择提醒方式。 |
| 语音对讲 | 对即时干预类报警，优先通过省平台语音对讲入口播放审核后的固定话术。 |
| 本地语音模型 | 首版用于播放标准话术，不用于自由生成未经审核的司机喊话内容。 |
| 司机回复识别 | 可作为首版可选能力，是否纳入 P0 由客户确认；未启用时只记录对讲和观察结果。 |
| 纠正检测 | 可基于页面字段、报警状态、视频帧和规则判断；无法确定时标记为无法判断，不默认通过。 |
| 异常接收 | 未纠正、无法判断或高风险报警，必须通知值班业务人员接收。 |
| 企业通知 | 首版提供企业负责人话术、一键复制和人工拨打入口；无人值守自动外呼需另行确认责任边界。 |
| 记录留痕 | AI 处理记录台账必须一键可查，记录所有 AI 参与和人工确认动作。 |

## 第2章 平台定位与建设价值

### 2.1 项目定位

本项目不是单纯的报警查询工具，也不是一个替代省平台的监管系统，而是面向三客一危车辆动态监管场景的 **“省平台报警第一处置辅助系统”**。

系统通过浏览器插件嵌入现有工作流，在报警出现后辅助监控人员完成“看见报警、读取信息、匹配规则、提醒司机、观察纠正、通知人工、生成记录”的过程。它的核心价值不是发现报警，而是把报警产生后的高压、重复、强责任处置流程变成可执行、可留痕、可复核的管理闭环。

### 2.2 建设价值

| 价值方向 | 说明 |
| --- | --- |
| 响应更及时 | 报警弹窗出现后由插件辅助识别和打开，减少人工漏看和慢处理。 |
| 处置更标准 | 按官方规则和客户 SOP 选择文本、语音、内部确认或企业通知方式。 |
| 干预有留痕 | 文本下发、语音对讲、提醒话术、按钮结果、司机回复和纠正检测均进入记录。 |
| 风险可升级 | 未纠正、无法判断和高风险报警自动形成事件并通知值班业务人员。 |
| 沟通更高效 | 事件详情页提供企业负责人沟通话术、关键信息复制和人工拨号入口。 |
| 责任可复盘 | AI 处理记录台账可按时间、车牌、企业、报警类型和状态查询。 |
| 边界更清楚 | 高风险、低置信度、无法判断等场景保留人工确认，降低自动化误判风险。 |

### 2.3 首版建设边界

首版重点验证“报警第一处置闭环”。以下能力属于首版范围：

1. 报警弹窗监听、报警列表兜底和报警详情读取。
2. 官方规则和客户 SOP 匹配。
3. 页面按钮触发，包括查看报警、文本下发、语音对讲等。
4. 固定话术文本提醒和本地语音模型对讲提醒。
5. 司机提醒后的纠正检测。
6. 值班业务人员短信通知和事件详情页。
7. 企业负责人沟通话术、一键复制和人工拨打入口。
8. AI 处理记录台账。

以下能力不纳入首版主验收：

1. 自动误报申诉提交。
2. 正误报最终自动判定。
3. 申诉处理。
4. 日报、周报、月报和正式统计报表导出。
5. 移动端远程接手完整工作流。
6. 管理人员看板。
7. 车辆巡检。
8. 驾驶员风险画像。
9. 企业风险排名。
10. 月度安全分析报告。
11. 无人值守自动电话外呼。
12. 录音归档。
13. 企业微信深度集成。
14. 复杂短信平台、批量群发和短信运营统计。

## 第3章 总体架构设计

系统采用五层架构：底层依托省平台页面能力，中间通过浏览器插件完成页面读取和按钮触发，通过规则引擎与 AI 辅助判断形成处置建议，再通过短信和事件详情页交给值班业务人员，最终沉淀到 AI 处理记录台账。

### 3.1 省平台页面与车辆监管数据层

该层包括省平台报警弹窗、报警列表、报警详情、视频画面、文本下发、语音对讲、证据导出、车辆档案、驾驶员信息和企业信息等现有能力。系统只读取和触发省平台已经具备的页面能力，不绕过省平台业务规则。

### 3.2 浏览器插件采集与执行层

该层负责监听报警弹窗、读取 DOM 字段、打开报警详情、识别页面按钮状态、触发文本下发和语音对讲等动作。页面结构变化、按钮不可用、读取失败或触发失败时，必须显式提示人工接管。

### 3.3 规则引擎与 AI 辅助判断层

该层负责匹配官方报警规则、客户 SOP、报警类型、风险等级、视频状态和页面字段，并结合 VLM 视频帧辅助判断司机状态。LLM 只用于生成审核模板内的摘要、企业沟通话术和记录说明，不用于未经审核的自由处置。

### 3.4 事件通知与人工协同层

该层负责对未纠正、无法判断或高风险报警生成事件记录，并通过短信通知值班业务人员。值班业务人员进入事件详情页后，可查看关键信息、复制话术、人工拨打企业负责人电话并记录处置结果。

### 3.5 AI 处理记录台账层

该层保存 AI 识别、规则匹配、文本下发、语音对讲、司机回复、纠正检测、短信通知、详情页查看、复制、拨打和人工备注等记录，用于日常查询、复盘和责任追踪。

| 事件通知与人工协同 | 值班短信与事件详情页 | 对未纠正、无法判断和高风险报警通知值班业务人员接收。 |
| 事件通知与人工协同 | 企业负责人沟通辅助 | 生成可复制话术和人工拨号入口。 |

### 4.2 报警监听与信息读取

| 编号 | 功能点 | 功能描述 | 业务规则 |
| --- | --- | --- | --- |
| F01 | 报警弹窗监听 | 监听省平台实时报警弹窗，读取报警类型、车牌、报警时间和查看报警入口。 | 弹窗监听失败时从报警列表兜底，仍失败则提示人工接管。 |
| F02 | 报警列表读取 | 读取报警列表中的报警类型、车牌、企业、驾驶员、状态和时间等字段。 | 读取字段必须标记来源，避免把推测字段当作事实字段。 |
| F03 | 报警详情读取 | 打开报警详情页，读取速度、位置、车辆状态、视频状态和页面处理状态。 | 页面字段缺失时标记为缺失，不自动补全。 |
| F04 | 证据信息采集 | 记录报警截图、视频帧、速度曲线、页面状态和按钮触发结果。 | 证据缺失时不能直接归为已纠正。 |

### 4.3 官方规则和 SOP 匹配

| 编号 | 功能点 | 功能描述 | 业务规则 |
| --- | --- | --- | --- |
| F01 | 报警类型规则 | 将官方报警规则转化为可配置规则，包括提醒方式、纠正标准和升级条件。 | 官方规则优先，客户 SOP 作为补充。 |
| F02 | 客户 SOP 匹配 | 按客户内部管理要求匹配文本、语音、内部确认或企业沟通。 | SOP 未确认时标记为待业务确认。 |
| F03 | 风险等级判断 | 根据报警类型、时间段、持续状态、视频判断和页面字段形成风险等级。 | 高风险报警必须进入人工确认。 |
| F04 | 处置路径选择 | 输出文本下发、语音对讲、内部确认、事件通知或暂不处理建议。 | 不默认文本和语音都做，避免重复骚扰司机和责任不清。 |

### 4.4 司机提醒与纠正检测

提醒方式不默认“文本+语音都做”。原则如下：

1. 官方要求即时人工干预或喊话提醒的报警，语音对讲必做，文本仅作补充或失败兜底。
2. 需要司机即时纠正的驾驶行为类报警，语音对讲优先。
3. 文本下发用于页面能力限制、语音失败、客户 SOP 要求或需要补充记录的场景。
4. 设备类、调度类、事后类报警不默认喊司机，优先进入内部确认或企业通知话术生成。
5. 所有司机提醒话术使用审核后的固定模板，避免 AI 自由生成造成责任边界不清。

| 报警类型 | 首版提醒方式 | 已做到位判定 |
| --- | --- | --- |
| 驾驶员突发情况报警 | 语音对讲必做 | 驾驶员头部/身体回到驾驶员监控区域，报警不再持续。 |
| 生理疲劳报警 | 语音对讲必做 | 车辆降速并就近安全停车，或报警状态解除；是否必须停车休息固定时长待业务确认。 |
| 手部脱离方向盘报警 | 语音对讲必做 | 手部恢复规范驾驶状态，报警不再持续。 |
| 超时驾驶报警 | 语音对讲优先 | 车辆安全停车休息；20 分钟休息字段和判定口径待业务确认。 |
| 超速驾驶报警 | 语音对讲优先 | 车速下降到限速阈值以下，或平台超速状态解除。 |
| 夜间异动报警 | 语音对讲优先 | 车辆停止运行或降至风险阈值以下；阈值口径待业务确认。 |
| 接打手持电话报警 | 语音对讲优先 | 视频中驾驶员停止接打手持电话，报警不再持续。 |
| 抽烟报警 | 语音对讲优先 | 视频中驾驶员停止抽烟，报警不再持续。 |
| 未系安全带报警 | 语音对讲优先 | 视频中驾驶员已规范系好安全带，报警不再持续。 |
| 分心驾驶报警 | 语音对讲优先 | 驾驶员目视前方、未低头、未接触手机，报警不再持续。 |
| 驾驶员身份识别报警 | 语音或文本提醒，口径待确认 | 身份识别成功或驾驶员完成身份核验；误报处理口径待业务确认。 |
| 电子围栏报警 | 内部确认优先 | 车辆返回允许范围，或企业确认合法运营/调度安排。 |
| 离线位移报警 | 内部确认 | 定位数据恢复正常，或企业核实离线位移原因。 |
| 超员驾驶报警 | 内部确认优先 | 企业或现场确认人数恢复合规；平台字段待业务确认。 |
| 设备故障报警 | 摄像头偏离/遮挡可语音提醒，其他进入内部确认 | 摄像头恢复正常，或定位/GNSS 状态恢复；细分口径待业务确认。 |
| 疑似事故报警 | 直接内部确认 | 由内部人员即时核查，属于高风险报警。 |

凡无法用省平台字段、视频状态或客户 SOP 明确判断的事项，都记录为“无法判断”，同时通知值班业务人员接收，不在首版里硬写成自动通过。

### 4.5 值班业务人员短信与事件详情页

内部确认触发条件固定为三类：

1. 司机提醒后未纠正。
2. 系统无法判断是否纠正。
3. 高风险报警。

触发后，系统第一时间发送手机短信给值班业务人员。

短信建议模板：

> 【三客一危报警处置】{车牌号} {报警类型} {纠正检测结果}。时间：{报警时间}，企业：{企业名称}。请点击查看处置详情：{详情链接}

事件详情页建议提供三组可复制内容：

1. 关键信息包：车牌、企业、驾驶员、报警类型、报警时间、地点、当前状态、已提醒方式、检测结果。
2. 企业负责人话术：AI 根据当前情况生成的完整沟通话术。
3. 内部备注：用于值班业务人员记录“已联系、无人接听、企业已反馈、需继续跟进”等结果。

### 4.6 企业负责人沟通辅助

话术结构为：

> {企业/负责人}，{车牌号} 于 {报警时间} 在 {地点} 发生 {报警类型}，驾驶员/车辆出现 {具体行为或状态}，已违反 {对应规则或管理要求}。平台已进行 {文本下发/语音对讲} 提醒，当前 {未纠正/无法判断/需企业核实}。请立即联系驾驶员或安排人员处理，并反馈处置结果。

首版生成的是可复制、可拨打的人工辅助信息，不做无人值守自动外呼。后续如果要接入自动外呼、录音归档或企业微信，需要单独确认责任边界、授权范围、号码来源、录音保存和合规要求。

### 4.7 AI 处理记录台账

首版 AI 相关处理记录台账必须一键可查可看。它不是正式统计报表，也不是管理大屏，但要能还原每次报警从识别到人工触达的过程。

建议查询条件：

1. 时间范围。
2. 车牌号。
3. 企业名称。
4. 报警类型。
5. 处理状态：已纠正、未纠正、无法判断、高风险、人工已接收。
6. 值班业务人员。
7. 是否已生成企业通知话术。
8. 是否已复制关键信息或拨打企业负责人电话。

建议记录字段：

1. 报警 ID 或页面可见标识。
2. 车牌、企业、驾驶员、报警类型、报警时间、地点。
3. 速度、车辆状态、视频/截图状态。
4. 司机提醒方式、提醒话术、提醒时间、按钮触发结果。
5. 纠正检测结果和证据说明。
6. 短信通知时间、接收人、详情页查看状态。
7. AI 生成的企业负责人沟通话术。
8. 关键信息复制、电话拨打、人工备注等处置动作。

## 第5章 关键业务流程

### 5.1 报警第一处置闭环

```text
省平台产生报警
    ↓
浏览器插件监听报警弹窗/报警列表
    ↓
读取报警类型、车牌、企业、驾驶员、时间、速度、位置、车辆状态等页面字段
    ↓
匹配官方报警规则和客户 SOP
    ↓
按规则选择文本下发、语音对讲、内部确认或暂不处理
    ↓
提醒司机并记录提醒方式、话术和按钮结果
    ↓
检测司机是否纠正或风险是否解除
    ↓
已纠正：记录 AI 处理台账，流程结束
未纠正/无法判断/高风险：生成事件记录并短信提醒值班业务人员
    ↓
值班业务人员点击短信链接进入事件详情页
    ↓
查看关键信息、AI 处置建议和企业负责人沟通话术
    ↓
一键复制关键信息/完整话术，或人工拨打企业负责人电话
    ↓
记录查看、复制、拨打、人工确认等动作到 AI 处理记录台账
```

### 5.2 AI 识别与人工确认流程

AI 识别流程应以事实字段、规则判断和人工确认分层处理：

1. 插件读取省平台页面可见字段，形成事实字段。
2. VLM 对视频帧中的驾驶行为、设备状态和是否纠正进行辅助判断。
3. 规则引擎结合官方规则和客户 SOP 输出建议动作。
4. LLM 生成审核模板内的摘要和沟通话术。
5. 高风险、低置信度、无法判断和字段缺失时，进入人工确认。
6. 人工确认结果写入 AI 处理记录台账，作为后续复盘依据。

### 5.3 企业通知与事件接收流程

企业通知流程不建议首版直接做无人值守自动外呼。建议先完成值班业务人员接收和人工辅助沟通：

1. 系统识别未纠正、无法判断或高风险报警。
2. 自动生成事件记录。
3. 向值班业务人员发送短信。
4. 值班业务人员打开事件详情页。
5. 查看报警信息、司机提醒记录、纠正检测结果和 AI 话术。
6. 一键复制企业负责人沟通内容。
7. 人工拨打企业负责人电话，或按客户确认方式通知企业。
8. 记录查看、复制、拨打和人工备注。

### 5.4 AI 处理记录追溯流程

AI 处理记录台账用于解决“AI 做过什么、何时做的、结果是什么、谁接收了、谁确认了”的追溯问题。每条记录应保留报警来源、字段读取、AI 判断、规则命中、页面按钮触发、短信通知、详情页查看、人工操作和最终状态。

## 第6章 重难点与应对策略

### 6.1 省平台无接口与页面结构变化

首版采用浏览器插件和页面自动化方式，依赖省平台 DOM、弹窗和按钮结构。若省平台页面改版、弹窗样式变化、按钮名称变化或权限变化，插件读取和触发可能失效。

应对策略：

1. 字段读取必须有来源标记和失败提示。
2. 关键 DOM 选择器建立多策略兜底。
3. 报警弹窗失败时，使用报警列表和报警查询兜底。
4. 按钮触发失败时，不静默跳过，必须提示人工接管。
5. 试运行期间记录失败样本，用于页面适配迭代。

### 6.2 VLM 纠正判断不稳定

夜间、遮挡、低码率、摄像头偏移、驾驶员姿态差异和多路视频画面会影响 VLM 判断。首版不能把 VLM 判断作为唯一处置依据。

应对策略：

1. 已纠正、未纠正和无法判断三类结果必须区分。
2. 低置信度或证据不足时进入人工确认。
3. 高风险报警即使 AI 判断已缓解，也建议人工复核。
4. 试运行期收集真实样本，逐步校准判断规则。
5. 所有判断保留视频帧、时间点和说明。

### 6.3 语音对讲与司机回复识别边界

语音对讲依赖省平台通道、本地语音播放设备、浏览器权限和现场网络。司机回复识别还涉及车载对讲回音、噪声和隐私边界。

应对策略：

1. 语音话术使用固定审核模板。
2. 语音播放失败时，提示文本下发或人工接管。
3. 司机回复识别作为可选能力，由客户确认是否纳入首版。
4. 未启用司机回复识别时，不影响记录对讲动作和纠正观察。
5. 对讲、回复和观察结果都进入台账。

### 6.4 短信通知与事件详情安全

短信链接涉及报警信息、车辆、驾驶员、企业和处置记录。需要控制访问权限和数据范围。

应对策略：

1. 短信接收人由客户确认。
2. 详情页访问需要身份校验或有效期控制。
3. 手机号、驾驶员和企业联系人信息需要脱敏展示。
4. 链接打开、复制、拨打和备注都写入记录。
5. 短信发送失败必须提示人工处理。

### 6.5 责任边界和客户制度配合

报警处置涉及安全责任，系统上线不仅是技术上线，也需要客户明确处置 SOP、提醒话术、通知责任人和人工确认边界。

应对策略：

1. 合同签订后逐条确认报警类型处置规则。
2. 固定话术由客户审核确认后使用。
3. 高风险、无法判断和低置信度保留人工确认。
4. 首版不做无人值守自动外呼和最终责任判断。
5. 记录台账用于复盘和责任追踪，不替代客户管理制度。

## 第7章 实施建议

### 7.1 总体实施路径

建议采用“页面适配先行、规则小范围验证、语音干预试点、记录台账闭环、再逐步扩展”的路径推进：

1. 确认省平台登录方式、页面结构、报警弹窗、报警列表和报警详情字段。
2. 选取 3 至 5 类高频报警作为首批试点。
3. 配置官方规则、客户 SOP 和固定提醒话术。
4. 完成浏览器插件读取、按钮触发、语音对讲和记录留痕。
5. 建立未纠正、无法判断和高风险报警的短信通知与事件详情页。
6. 试运行 2 至 4 周，收集失败样本、误判样本和人工确认结果。
7. 根据试运行结果扩展报警类型、优化规则和完善台账查询。

## 第8章 验收建议

### 8.1 功能验收

功能验收建议按实际处置链路逐项确认：

1. 插件能够识别省平台实时报警。
2. 插件能够读取报警类型、车牌、企业、驾驶员、报警时间等核心字段。
3. 插件能够按规则选择文本下发、语音对讲、内部确认或不处理。
4. 插件能够打开对应报警详情，并触发文本下发或语音对讲按钮。
5. 插件能够使用固定话术提醒司机。
6. 插件能够检测司机是否纠正，或给出“无法判断，需人工确认”。
7. 未纠正、无法判断或高风险报警时，系统能够生成事件记录并短信通知值班业务人员。
8. 值班业务人员能够通过短信链接查看事件详情。
9. 事件详情页能够一键复制关键信息和 AI 生成话术。
10. 事件详情页能够提供企业负责人电话入口，支持人工一键拨打。
11. AI 处理记录台账能够记录提醒、检测、短信、查看、复制、拨打和人工确认过程。
12. AI 处理记录台账能够按时间、车牌、企业、报警类型和处理状态一键查询查看。
13. 插件操作失败时不静默跳过，必须提示人工接管。

### 8.2 数据验收

数据验收建议关注字段完整性、证据留存和操作可追溯性：

1. 报警字段能关联车牌、企业、驾驶员、时间、地点、速度和报警类型。
2. 司机提醒动作保留方式、话术、时间、按钮结果和操作来源。
3. 纠正检测保留结果、判断依据、视频帧或页面字段说明。
4. 短信通知保留接收人、时间、发送状态和详情页查看状态。
5. 复制、拨打、人工备注等动作保留操作人和时间。
6. 字段缺失、读取失败、按钮失败和 AI 无法判断都有异常记录。

### 8.3 AI 能力验收

AI 能力验收建议采用试运行方式，不建议以上线首日结果作为最终验收依据。

验收指标可包括：

| 指标 | 说明 |
| --- | --- |
| 报警读取成功率 | 报警出现后插件是否能正确捕获并读取核心字段。 |
| 页面按钮触发成功率 | 文本下发、语音对讲等按钮是否能被正确触发并记录结果。 |
| 纠正检测一致率 | AI 判断已纠正、未纠正、无法判断与人工复核结果的一致程度。 |
| 无法判断兜底率 | 证据不足时是否能正确进入人工确认，而不是误判通过。 |
| 短信通知成功率 | 事件触发后短信是否成功送达指定值班业务人员。 |
| 证据留存完整率 | 报警截图、视频帧、话术、按钮结果、短信和人工记录是否完整。 |

试运行期间产生的人工复核结果可用于校准识别阈值和业务规则。正式验收指标建议基于试运行样本与双方确认的业务口径确定。

### 8.4 边界说明

1. AI 能力用于辅助报警第一处置，不替代人工最终责任判断。
2. 省平台页面结构、账号权限和网络状态会影响插件执行效果。
3. 自动识别结果不得在低置信度、高风险和证据不足场景下直接闭环。
4. 首版企业负责人电话入口为人工辅助拨号，不是无人值守自动外呼。
5. 后续如接入自动外呼、录音归档、企业微信或正式报表，需要单独确认范围、合规和验收标准。

## 第9章 待确认事项

1. 省平台各类报警页面的真实按钮名称和操作路径。
2. 省平台是否能稳定读取速度、停车、报警解除、视频状态等字段。
3. 生理疲劳报警是否必须停车休息，以及具体休息时长。
4. 超时驾驶报警停车休息 20 分钟的页面可见字段和判定方式。
5. 夜间异动报警是否按 2:00-5:00、10/30 公里阈值直接判定。
6. 驾驶员身份识别报警是否纳入首版自动提醒。
7. 电子围栏、超员、设备故障类报警是否需要司机提醒，还是只内部确认。
8. 值班业务人员短信接收人、短信模板、详情页访问方式和手机号权限。
9. 企业负责人通讯录、通知边界、一键拨打是否可用。
10. 司机语音回复识别是否纳入首版，还是作为后续增强能力。
11. AI 处理记录台账字段、保存周期和查询条件。
12. 试运行期样本数量、人工复核方式和 AI 验收指标。

## 第10章 后续演进

后续可以与业务任务、任务清单或项目协作系统打通。规则稳定后，把“已经确认规则、重复发生、人工只是机械核对”的工作逐步交给 AI 自动处理；仍然不清楚、风险高、涉及责任边界的事项继续保留人工确认。

可放到后续版本的能力包括：

1. 自动外呼和录音归档。
2. 企业微信或短信平台深度集成。
3. 正式日报、月报、管理看板。
4. 自动申诉辅助。
5. 企业风险画像和排名。
6. 与业务任务系统联动派单、跟进和闭环。

## 当前结论

三客一危省平台 AI 报警处置助手的首版价值不在于做大平台，而在于把最急的报警第一处置责任链路跑通：报警及时识别、按规则提醒司机、纠正检测、异常及时短信通知值班业务人员、生成企业负责人沟通话术，并保留 AI 处理记录台账一键可查可看。
