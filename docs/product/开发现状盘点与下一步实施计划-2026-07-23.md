## 1. 本文结论

当前项目已经完成报警采集、规则治理、真实自动动作执行器、跨账号防重、五来源报表取数框架、服务端校验与 XLSX 生成等主体开发，自动化测试全部通过。

“代码已实现”“自动测试通过”和“真实平台已验收”是三个不同状态。本文只把有当前代码、测试或真实页面证据支持的事项列为完成。

## 2. 已完成内容

### 2.1 报警采集与展示

- 已接入正式实时报警、待处理正式报警、技术检测、预报警和历史报警等来源。
- `REALTIME` 与 `PENDING` 在界面中统一归入“正式报警”，同时保留原始来源证据。
- 已支持对已观察到的报警来源进行独立轮询；省平台原生请求优先，静默时才执行受控兜底轮询。
- 已实现字段标准化、跨接口合并、来源追踪、冲突保留、重复响应抑制和加密本地台账。
- 技术检测保留诊断字段，正式报警与技术检测不会再只显示一套通用字段。
- 401/403、登录失效、字段变化和接口异常会停止对应轮询或进入恢复流程，不会用旧数据伪装成功。

### 2.2 报警处理状态、去重与并发控制

- 报警处理状态已统一为：
  - `UNPROCESSED`
  - `EXECUTING`
  - `PROCESSED`
  - `MANUAL_REQUIRED`
  - `UNKNOWN`
- 已按报警唯一标识、来源和车辆等信息建立稳定事件键，并保留平台状态变化。
- 已实现后台 `RESPONSE_PLAN` 全局租约，防止同一报警被多个账号或多个插件重复处理。
- 动作执行与具体省平台标签绑定，避免多个标签或多个账号串用会话。
- 已处理、结果未知或已进入执行中的报警不会被另一账号重复下发。
- 语音、文本/TTS、平台“已处理”登记分别记录独立回执；只有明确成功回执才能推进到下一阶段。

### 2.3 真实自动动作链路

- 运行模式已固定为真实自动运行；运行时代码已删除演练、沙箱、模拟动作、单条手工触发和人工动作重试入口。
- 插件可在命中已发布规则后自动进入“值班值守监控 → 实时监控”，并核对目标报警和车辆。
- 当前已开放的真实自动规则为：`PREWARNING + 超速驾驶`。
- 已实现固定顺序：
  1. 自动进入目标车辆监控页面；
  2. 下发已审核的固定语音；
  3. 语音明确结束后下发相同固定文本/终端 TTS；
  4. 两个动作取得明确成功回执后登记平台“已处理”；
  5. 同步后台处理状态和动作审计。
- 语音明确失败时可以按已发布规则执行固定文本兜底，同时转人工关注。
- 语音或平台结果为未知、超时或阻断时会立即停止后续动作，不把未知结果当成功。
- 每个动作阶段都会重新核验实名身份、当前班次、企业范围、省平台会话、执行标签、后台租约、已发布规则和已审核资产。

### 2.4 超速报警话术与音频资产

- 固定话术已经审核并发布：

  `驾驶员，平台已报警，车辆超速驾驶，请降速安全行驶。`

- 已生成和管理文本、MP3 试听版、WAV 母版及平台用 8kHz、16bit、单声道裸 PCM。
- 已修复后台发布 WAV 与平台裸 PCM 的格式差异：先校验已发布 WAV 的哈希和格式，再只提取 WAV 的 `data` 区发送，避免把 WAV 文件头作为音频发送。
- 当前本地已发布规则包为 `speeding-live-v1`，文本和语音资产均为已审核版本。

### 2.5 五来源报表主体能力

五个来源已经固定为：

- `ALARM_DISPOSAL_RATE`
- `ALARM_PROCESSING_RATE`
- `ALARM_CENTER`
- `VEHICLE_BASE_INFO`
- `TRACK_COMPLETENESS`

已经完成：

- 五来源真实接口白名单契约、固定方法、路径、分页、响应行路径、总数路径和字段签名。
- Django 报表任务、来源批次、分页、车辆日报行、快照和导出任务数据模型。
- 插件每分钟查询已有报表任务，领取任务后在当前已登录省平台标签中执行白名单取数。
- Cookie、Authorization、验证码和密码不上传 Django；平台请求仍由浏览器当前授权会话发出。
- 分页幂等上传、冲突检测、缺页检查、总页数/总行数校验、字段签名校验、周期和筛选范围校验。
- 任一来源缺页、字段变化、日期错误、范围无法证明或接口失败时进入 `DATA_INCOMPLETE`，不生成正式文件。
- 报警日报、周报、月报复用同一处理链，按平台企业 ID 拆分三个独立来源。
- 每家企业生成固定三个子表：
  1. `处置率报表`
  2. `处理率报表`
  3. `报警查询报表`
- 车辆动态监控日报以车辆基础信息为左表、轨迹完整率为右表，车辆 ID 为首选关联键。
- 已实现上线、未上线、空定位过滤、未来定位异常、在线零里程、轨迹不完整、重复 ID、一对多和企业冲突等规则。
- 已实现企业工作簿、过滤清单、异常清单、明细审计和任务级全局异常文件。
- 关键异常未解决前禁止正式发布；过滤记录可以进入人工审核。

### 3.2 自动报表调度缺失

- 插件已经能每分钟领取并执行“已有任务”，但 Django 目前不会自动创建最近周期任务。
- 仍需自动确保以下任务：
  - 每天创建前一日企业报警日报；
  - 每天创建前一日车辆动态监控日报；
  - 每周创建上一完整周企业报警周报；
  - 每月创建上一自然月企业报警月报。
- 自动创建必须使用数据库唯一约束或等价幂等机制，防止多插件、多进程重复建任务。
- 当前取数完成后会自动生成数据库快照并进入 `REVIEW_REQUIRED`；人工审核通过后，单企业 XLSX 和任务级 ZIP 仍需由页面或 API 发起导出，尚未自动预生成可下载文件。

### 3.3 车辆状态范围仍未配置

- 业务要求同时包含“营运”和“营运不考核”。
- 代码要求配置至少两个已审核的平台车辆状态码，但当前 `PLATFORM_REPORT_VEHICLE_STATUS_CODES` 尚未配置。
- 在状态码未由真实页面或真实请求证据确认前，任务会以 `VEHICLE_STATUS_SCOPE_UNCONFIRMED` 阻断；这是正确的完整性保护，不应通过猜测状态码绕过。

### 3.4 五来源真实结果验收未完成

- 虽然接口契约和合成测试已通过，但还没有形成五个来源的真实完整批次并完成以下对账：
  - 平台总页数、总行数与插件上传数一致；
  - 各企业有效行数之和等于来源有效总行数；
  - 企业三表与运营团队人工拆分结果逐行一致；
  - 车辆日报上线/未上线、空定位、零里程和轨迹完整率与人工模板逐行一致；
  - 未知企业、车牌兜底、一对多和企业冲突均进入正确清单。
- 正式模板的最终表头、字段顺序和样式仍需用运营团队确认的净化模板做最终验收。

### 3.5 后端自启动和生产部署未完成

5. Agent 只读观察；不得代替插件点击报警、语音、文本、查询、导出或已处理按钮。
6. 插件自动轮询，选择新鲜、未处理、字段完整且命中 `speeding-live-v1` 的超速预报警。

### 阶段三：补齐报表自动任务调度

5. 对重复请求、多插件并发、服务重启和跨零点场景增加回归测试。

## 6. 最终完成判定

只有以下条件全部满足，项目才能标记为“开发和验收完成”：

- 真实超速报警已完成自动导航、语音、文本/TTS和平台已处理登记，且取得明确回执。
- 多账号同时运行时同一报警只执行一次。
- 一个完整值班周期内没有未解释的重复、并发串号或静默失败。
- 日报、周报、月报和车辆动态监控日报任务可以自动创建并自动取数。
- 五来源真实数据完整性校验通过，并与人工黄金样本逐行一致。
- 企业三表、车辆日报、过滤清单和异常清单可以审核并下载。
- 后端能可靠自启动，插件在用户登录后无需额外人工指令即可工作。
- 所有变更均已测试、独立提交并推送。
- 已确认服务端 commit 完成生产部署、迁移、健康检查和回滚点记录。
