# 省平台语音对讲技术溯源

日期：`2026-07-20`  
调研方式：当前线上静态资源只读检查 + 历史工程记录交叉核对  
安全边界：未点击语音对讲、未申请麦克风权限、未建立 WebSocket、未向车辆发送音频。

## 1. 结论

目前可以高置信确认“语音对讲”的启动来源和总体技术路线，但不能完全确认可直接实现生产适配器所需的全部协议细节。

已确认：

- 语音对讲是人工实时双向通话，不是固定文案播报；
- 入口位于实时监控页车辆详情区域；
- 按钮受账号权限、车辆在线、非对讲中、非加载中等条件控制；
- 点击后调用实时音频传输启动接口；
- 启动请求成功后读取 `httpUrl` 和 `fileName`；
- 页面随后打开对讲组件；
- 当前线上主包仍定义启动、控制和保活三个接口；
- 历史组件快照显示对讲使用浏览器麦克风、WebSocket 和 PCM 音频。

未完全确认：

- 当前线上 WebSocket URL 的实际结构；
- WebSocket 鉴权放在 URL、Cookie、Header 还是首帧；
- WebSocket 子协议；
- 当前线上音频是否仍为 8kHz、16bit、单声道 PCM；
- 320 采样点一帧是否仍有效；
- 二进制帧是否带自定义头、序号或长度字段；
- 服务端回传音频格式；
- 保活周期、保活成功判定；
- 正常关闭、异常关闭的状态码和回执；
- 设备离线、通道占用、无权限、麦克风拒绝时的完整错误码。

因此，当前不能宣称已经“完全确认语音协议”或可以安全编写无人值守对讲发送器。

## 2. 当前线上证据

### 2.1 当前加载版本

实时监控页当前加载的主要前端资源包括：

- `/static/js/app.5f1290df.js`
- `/static/js/chunk-759da220.3f44d3c7.js`

这与 2026-06-30 历史快照中的 chunk 名称已经不同，说明不能直接把旧压缩包当成当前稳定接口文档。

### 2.2 当前接口定义

当前线上 `app.5f1290df.js` 仍明确包含：

```http
POST /schedule-service/sendVideo/sendRealAudioTransmissionMessage
POST /schedule-service/sendVideo/sendRealAudioControlMessage
POST /gpsp-service/sendVideo/sendRealAudioKeepMessage
```

对应判断：

| 接口 | 当前用途判断 | 证据等级 |
| --- | --- | --- |
| `sendRealAudioTransmissionMessage` | 启动/取得实时音频传输信息 | 当前线上代码确认 |
| `sendRealAudioControlMessage` | 关闭或控制对讲 | 当前线上代码确认，具体参数仍需抓包 |
| `sendRealAudioKeepMessage` | 对讲保活 | 当前线上代码确认，周期与回执仍需抓包 |

### 2.3 当前按钮与启动流程

当前实时监控 chunk 中的 `sendIntercom()` 显示，按钮执行前至少检查：

- 当前账号具有对应功能权限；
- `currentCarInfo.onlineStatus == 1`；
- `intercom.modalShow == false`；
- `isLoadingIntercom == false`。

当前启动请求的结构为：

```json
{
  "cameraIds": [1],
  "carId": "<当前车辆ID>",
  "streamType": 0,
  "subCode": 2
}
```

调用：

```http
POST /api/schedule-service/sendVideo/sendRealAudioTransmissionMessage
```

成功分支要求响应成功且第一条数据没有 `errDesc`，随后读取：

```json
{
  "httpUrl": "<实时音频地址>",
  "fileName": "<对讲文件名>"
}
```

页面把这些值写入对讲组件状态，并打开对讲弹窗。

这说明 `sendRealAudioTransmissionMessage` 是“建立对讲前的信令接口”，不是直接上传整段语音文件的接口。

## 3. 历史静态组件证据

历史工程记录来自 2026-06-30 时点前端静态组件，显示：

- 浏览器申请麦克风权限；
- 单声道、16bit、8000Hz PCM；
- 320 个采样点一帧；
- 使用 WebSocket 二进制发送；
- 服务端音频回传后由 `<audio>` 播放；
- 没有录音设备或 WebSocket 关闭时结束对讲；
- 关闭接口带 `filename`、`subCode:4`、`closeType:0` 等参数；
- 保活接口带 `carId`、`filename`、`streamType`、`subCode` 和 `result`。

这些信息与当前线上启动接口仍然吻合，但音频帧和关闭/保活参数尚未在当前版本重新抓包，所以证据等级只能标为“强线索”，不能标为“当前契约已确认”。

## 4. 技术链路判断

```text
用户选择车辆
→ 页面检查账号权限、车辆在线和对讲占用状态
→ POST sendRealAudioTransmissionMessage
→ 返回 httpUrl + fileName
→ 打开 Intercom 组件
→ 申请麦克风权限
→ 建立实时音频 WebSocket
→ 浏览器采集并发送音频帧
→ 接收车辆端回传音频并播放
→ 周期调用 sendRealAudioKeepMessage
→ 结束时调用 sendRealAudioControlMessage
```

## 5. 对当前产品的影响

- 自动司机提醒继续使用“文本下发 + 终端 TTS 播读”。
- 语音对讲继续定义为值班人员手动实时通话。
- 不能把历史 PCM 线索用于自动播报固定 TTS。
- 不能因为按钮可点击就把对讲视为发送成功。
- 对讲成功至少需要分别记录：启动信令成功、WebSocket 建立、音频发送、服务端回传、保活状态和正常关闭。
- 当前扩展执行层继续阻断自动 `VOICE_INTERCOM` 是正确的。

## 6. 完全确认所需的最小授权测试

要把技术来源提升为“完整确认”，需要在客户明确授权的测试车辆上，由值班人员手动完成一次短时对讲，同时只采集脱敏技术元数据：

1. 启动接口的请求字段名、响应字段名和错误码；
2. WebSocket 地址的结构化摘要，凭据必须立即脱敏；
3. WebSocket 握手结果和子协议；
4. 前几帧二进制数据的长度、间隔和结构摘要，不保存实际语音内容；
5. 音频采样率、位深、声道和每帧采样数；
6. 保活接口的周期、请求字段和成功回执；
7. 人工结束时的关闭请求和 WebSocket 关闭码；
8. 麦克风拒绝、车辆离线或通道占用至少一种失败状态。

测试不得保存 Cookie、Authorization、Token、完整 WebSocket 凭据、司机语音或车辆端回传音频。

| WebSocket 鉴权、帧结构、保活周期、关闭码 | 低，必须真实授权抓包 |

最终结论：已经确认“从哪里启动、调用哪个信令接口、拿到什么连接信息”，但尚未完全确认“WebSocket 里具体怎样鉴权、怎样编码和怎样可靠结束”。
