# 多浏览器并发与技术栈决策

日期：2026-07-20  
状态：已采用

## 决策

- 目标容量为同时在线插件不超过 50 个。
- Django 是唯一业务后端；不并行建设 FastAPI。
- 本机开发保留 SQLite，生产必须使用 PostgreSQL。
- 当前后台继续使用 Django 模板；如后续出现复杂交互，优先渐进引入 Vue 3，不整体重写。
- 插件使用 REST、设备心跳和低频策略同步，不增加业务 WebSocket。
- 第一阶段不引入 Redis、Celery、Kafka。

## 并发控制

- `AlarmFact` 通过全局事件标识和业务指纹保持唯一。
- `CaptureSource` 为每个设备和幂等采集标识保存独立来源。
- 报警归并、工单和动作租约使用数据库事务；生产依赖 PostgreSQL 行级锁和唯一约束。
- `ActionLease` 保证同一报警同一动作类型最多一个有效租约；真实动作仍保持未授权阻断。
- 设备心跳为 60 秒周期，会话保活为管理员策略控制的 20—50 分钟周期，并加入设备错峰。

## 会话保活授权边界

平台方已确认允许定时点击模拟人工活动。实现只允许报警预处理页唯一“查询”按钮，不允许服务器或插件配置任意选择器。其他路由、登录页、验证码、人机挑战、目标缺失或目标重复全部安全跳过。该授权不包含文本、语音、查岗、申诉、忽略、正报或自动登录。

## 重新评估条件

仅当在线插件接近 300、PostgreSQL 优化后采集接口仍长期超时、报表明显阻塞采集，或出现高频流式接入要求时，才评估把无状态采集入口拆成独立服务。Django仍保留身份、权限、规则、审计和报表权威。
