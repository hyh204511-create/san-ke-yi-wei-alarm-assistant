# 三客一危平台 AI 报警干预助手 - MVP 风险收敛决策

> **历史 MVP 决策快照。** 本文用于解释早期范围收敛，不是当前产品权限与模块基线。当前基线见 [产品逻辑规划 V2](../product/三客一危值班助手-产品逻辑规划-v2.md)：监控、规则配置、规则审核职责分离；文本/语音双渠道；独立企业报表中心；完整 JSON 按敏感证据包管理。

## 决策结论

第一阶段不做“大而全监管平台”，只验证一条可运行、可追溯、可失败兜底的浏览器插件闭环：

三客一危平台报警弹窗监听 -> DOM 读取报警详情 -> VLM 识别视频帧 -> LLM 生成审核话术和记录摘要 -> 本地语音模型通过平台对讲干预司机 -> 观察司机是否纠正 -> 未纠正则电话或短信通知企业负责人 -> 生成报警记录并归档。

老板看板、移动端接手、复杂规则配置、自动巡检和深度统计仍保留在原型中用于演示全局方向，但不应作为第一阶段验收主线。

## 最危险的 3 个假设

1. 浏览器插件能长期稳定读取三客一危平台 DOM、弹窗和按钮状态。
2. VLM 能可靠判断司机是否已经纠正，且能适应夜间、遮挡、低码率和多摄像头画面。
3. 语音对讲、司机回复识别、电话/短信通知和记录归档可以用简单状态字段串起来。

## 第一阶段必须保留

- 报警弹窗监听与报警详情读取稳定性验证。
- DOM+VLM+LLM 识别流水线。
- 固定审核话术的文字下发和本地语音对讲。
- 司机回复识别作为可选能力，由客户确认优先级。
- 对讲后纠正观察窗口。
- 未纠正时通知企业负责人，并记录电话、短信或升级结果。
- 报警截图、视频帧、对讲话术、司机回复、观察结果、企业通知和处理时间线留痕。
- 报警记录草稿、主管确认、归档和基础台账导出。

## 第一阶段必须后置

- 全量报警类型覆盖。
- 多企业复杂 SOP 配置。
- 复杂通讯录、多级联系人和双向回执。
- 企业微信、短信平台的正式深度对接。
- 自动巡检和设备运维闭环。
- 管理看板的深度归因分析。

## 上线红线

- 插件读取失败必须显式告警，不能静默漏报警。
- 高风险、低置信度、司机未纠正和通知失败必须人工确认。
- 未完成文字或语音干预时，不能判断“已纠正”。
- 企业通知失败不能标记“已通知”。
- 报警记录必须保留版本、证据来源、操作人和时间线。
- 导出数据必须脱敏并留访问日志。
- 状态流转必须可审计、可回放。

## 原型已落实的风控调整

- 将产品主线收敛为“浏览器插件报警干预闭环”。
- 新增插件流水线状态：报警弹窗、DOM 读取、VLM 识别、LLM 话术、本地语音、司机回复、纠正观察、企业通知。
- 新增外部依赖健康检查：弹窗监听、DOM 读取、VLM、LLM、视频证据、文本下发、语音通道、本地语音模型、司机 ASR、电话网关、短信/消息通道。
- 对识别、文本下发、语音对讲、司机回复识别、纠正观察、企业通知、记录生成和归档加入阻断条件。
- 新增审计日志，记录关键动作、阻断原因和结果。
- 新增前端原型内状态机，禁止关键状态非法跳转。
- 新增数据一致性扫描，暴露“已归档但缺识别结果”“已处理但企业通知仍未完成”等矛盾状态。
- 新增角色权限模型：监控员、值班主管、管理层。
- 新增关键动作权限拦截：监控员不能归档记录、不能闭环高风险、不能导出报表。
- 新增报警记录版本链，归档必须绑定最后一版记录。
- 新增验收演练页面，内置主链路、非法状态、权限拒绝、记录版本、外部依赖和一致性扫描用例。

## 下一步

1. 用真实三客一危平台账号验证弹窗监听、DOM 读取和按钮触发稳定性。
2. 收集 20-50 条真实报警样本，建立 VLM 纠正判断基线。
3. 让客户确认司机语音回复识别是否进入第一阶段范围。
4. 定义正式状态机、记录版本模型和审计日志模型。
5. 再决定是否进入复杂企业通知、移动端接手、老板看板和自动巡检扩展。

## 原型内置验收用例

- 状态机阻断跳步归档。
- 状态机阻断通知伪成功。
- 主链路生成报警记录版本。
- 监控员权限拒绝归档。
- 主管权限允许归档。
- 一致性扫描发现记录缺失。
- 一致性扫描发现高风险无接手人。
- 外部依赖检查完整。
